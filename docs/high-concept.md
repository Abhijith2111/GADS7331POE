# High-Concept Document — The Tavern Master

## Pitch

> *"Tend bar at the edge of an empire. Five regulars, an LLM in the
> back room, and every conversation is one you've never had before."*

**The Tavern Master** is a single-player tavern simulator where the
player runs a small fantasy bar. Customers walk up to the counter one
at a time, with hand-authored personas (a paranoid wizard, a broke
bard, a smug noble, a gruff dwarf, a mysterious traveller). The player
greets them, sells food, drink, and rooms, haggles over prices, listens
for gossip, and accepts small fetch-quests. Every word a customer says,
and every haggle decision they make, is generated live by a **local
Large Language Model** through Ollama.

The fantasy is the small, warm one of running a place where stories
happen — *Disco Elysium* meets *Coffee Talk* meets *Skyrim* tavern
small-talk — except the small talk genuinely is fresh every play.

## Pillar features

1. **Five distinct, persistent personas.** Each customer is defined by a
   plain JSON file (name, voice, secret, coin purse, wants). Modders can
   add or rewrite personas without touching code.
2. **LLM-driven conversation.** Streaming, character-by-character replies
   in each persona's voice, conditioned on the persona card and the live
   world-state JSON.
3. **Haggling that actually changes prices.** When the player offers a
   price, the LLM responds in JSON: `{accept, counter_offer, line,
   walk_away}`. Counter-offers loop. The persona's `budget_gold` and
   `haggle_floor_pct` are enforced with hard clamps so the model can
   colour the negotiation but cannot break the economy.
4. **Gossip that travels.** Lines that read like rumours are extracted
   from the model's replies and re-injected into later customers'
   prompts as "what's already going round town", so the world remembers.
5. **One-off quests with a world to walk.** Customers occasionally
   offer schema-constrained fetch-or-rumour errands the player can
   accept. Once accepted, the player can leave the bar to a world map
   of four hand-authored locations and search a handful of hotspots
   per location for the target item. The LLM picks the location and
   hotspot when the quest is generated, and writes a single
   in-character "you found it" line on success. Reward lands in the
   gold counter and the player is whisked back to the bar.

## Where the LLM lives in the design

| Layer            | Generated by code | Generated by LLM |
| ---------------- | ----------------- | ---------------- |
| Game economy     | yes               | no               |
| Item catalogue   | yes               | no               |
| Persona facts    | yes (JSON)        | no               |
| Spoken dialogue  | no                | yes              |
| Haggle decision  | partial (clamps)  | yes              |
| Gossip lines     | no                | yes              |
| Quest titles & summaries | no        | yes              |
| Quest reward calculation | clamped to [5,40] | yes (within range) |
| Quest placement (location + hotspot) | clamped to known table | yes (chosen from a list) |
| World-map / hotspot art | yes (procedural) | no               |
| "You found it" narration | no        | yes (1-2 sentences, JSON-mode) |

The LLM never decides what the player owns, what items exist, or how
much gold the player has. It decides what is *said* and the soft beats
(accept/refuse, counter, walk away, "rumour"-flagged sentences). This
keeps the gameplay deterministic and savable while still letting the
LLM drive the social texture of the world.

## Why a *local* model is appropriate

A cloud LLM (OpenAI, Anthropic, etc.) would technically work, but a
**local model is a better fit** for this brief and this game for five
concrete reasons:

1. **Offline play.** The game must be runnable in a classroom or a
   demo lab without guaranteed Wi-Fi. Cloud APIs make that fragile.
2. **No per-token cost.** Players (and markers) can leave the game
   running and produce hours of dialogue without an API bill. This
   matters for a project where prompt iteration is part of the grade.
3. **Privacy.** Players can ask customers anything. A cloud provider
   would log those conversations to a third party. With Ollama, every
   prompt and response stays on `localhost`.
4. **Reproducibility for assessment.** Ollama supports a fixed `seed`
   parameter; combined with the same prompt and the same model tag,
   we can reproduce a specific demo scene on demand. Cloud APIs vary
   their outputs across versions.
5. **Modability.** Swapping `llama3.2:3b` for `qwen2.5:3b` or
   `mistral:7b` is one CLI flag. Players who own beefier hardware can
   move to a smarter model without us shipping a new build.

A 3-billion-parameter instruction model is genuinely good enough for
the role we ask of it: short, in-character, single-customer dialogue
plus small structured JSON decisions. Bigger models help, but the
gameplay does not require them — the design constrains the LLM's job
to *what small models are best at*.

## Tone and audience

The Tavern Master aims for a quiet, lived-in fantasy register — closer to
*Disco Elysium*'s street-corner conversations than to a high-fantasy
heroic epic. Target audience is "anyone who has spent more time in
*Skyrim* taverns than in *Skyrim* dungeons."

Content is text-only, with no graphic violence; persona prompts steer
the model toward light fantasy themes and away from shock content. A
transparency banner reminds players at all times that the dialogue is
machine-generated, and the player can hide it (`T`) but not before
they've seen it on launch.

## Success criteria for the build

- A clean clone runs on Windows in under 10 minutes from `setup.md`.
- A first-time player can have a coherent, in-character conversation
  with at least one customer within 30 seconds of launch.
- A haggle round-trip (offer → counter → accept) completes inside 6
  seconds on a 16 GB laptop using the default 3B model.
- Five personas are individually distinguishable in blind read-aloud
  tests of two-line excerpts.
- The world-state JSON visibly mutates on disk during play, making the
  LLM integration legible to a video reviewer.
